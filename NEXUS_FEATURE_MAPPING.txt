This document provides a thorough, exhaustive mapping of the features implemented
in the NEXUS Smart Load Balancer Simulator to the concepts, theories, and
algorithms studied across the lecture series (T1, T2, and T3).

NEXUS is not merely a technical tool; it is a pedagogical bridge that connects
the abstract principles of Distributed Systems (DS) and Cloud Computing with
tangible, real-time visualizations and simulations.

--------------------------------------------------------------------------------
PART I: PHILOSOPHICAL AND HISTORICAL CONTEXT
--------------------------------------------------------------------------------

1.1. THE EVOLUTION OF DISTRIBUTED SYSTEMS
As discussed in Lecture T1 (Brief Intro to DS), the transition from centralized
mainframes to distributed networks was driven by the necessity for Resource
Sharing and Cost Efficiency. NEXUS embodies this evolution by simulating a
cluster of autonomous computers (ServerNodes) that cooperate to handle 
web-scale traffic.

The distinction between a "Network" and a "Distributed System" is software. 
NEXUS is precisely the "Software built on top of a network" that makes the 
cluster appear as a single coherent entity to the user. This "Single System
Image" (SSI) is the holy grail of DS design, and NEXUS achieves this through
its centralized simulation engine and decentralized server models.

1.2. MAPPING THE CHALLENGES (LECTURE T1)
Lecture T1 outlines key implementation challenges:
- Heterogeneity: NEXUS addresses this by allowing different "Weights" for 
  servers, simulating a mix of high-performance and low-performance hardware.
- Scalability: The Auto-Scaling engine simulates horizontal scaling, the 
  primary solution to the scalability bottleneck.
- Failure Handling: The Failure Injector allows users to experience the three
  states of a fault: Fault -> Error -> Failure.

PART II: T1 DEEP DIVE - FUNDAMENTALS
--------------------------------------------------------------------------------

2.1. CLOCK SYNCHRONIZATION AND THE ARROW OF TIME
In a distributed system, the lack of a global clock (T1) leads to the need for
Logical Clocks. NEXUS implements a "Tick Engine."
- The Tick Loop (simulation.py): Each tick is a discrete unit of time. This
  mirrors Lamport's Logical Clocks where an event A happens before event B if
  tick(A) < tick(B).
- Physical vs. Logical Time: While the host machine uses physical time, the
  simulation relies on the "Tick Interval" (500ms) to maintain consistency.
  This allows for deterministic simulation, even if the host machine 
  experiences CPU jitter.

2.2. GLOBAL STATE AND SYSTEM SNAPSHOTS
Lecture T1 introduces the Chandy-Lamport algorithm for recording a consistent
global state.
- NEXUS Metrics Collector: This component captures the state of all 
  channels (WebSockets) and all processes (ServerNodes) at the end of every
  tick.
- Consistent Cuts: By locking the simulation state during the snapshot 
  process, NEXUS ensures that the "Global View" presented on the dashboard 
  contains no "Orphan Messages" or "Lost Requests," satisfying the criteria
  for a consistent cut.

2.3. MUTUAL EXCLUSION AND TOKEN-BASED ALGORITHMS
While not explicitly using a token, the Load Balancer itself acts as the 
"Critical Section Manager."
- Request Queuing: Only one server can handle a specific request ID at a time.
  This is a form of mutual exclusion on the "Request Resource."
- Centralized vs. Distributed: NEXUS initially uses a centralized model (The
  Load Balancer), but its Raft simulation introduces distributed consensus,
  moving towards the "Non-token based algorithms" described in T1/8-9.

2.4. ELECTION ALGORITHMS: THE BATTLE FOR LEADERSHIP
Lecture T1/6 discusses Bully and Ring algorithms.
- NEXUS Raft Leader Election: When the control plane starts, nodes initiate
  a voting process.
- Bully Algorithm Mapping: If we consider the server ID as the priority,
  the Raft election is a modernized, more resilient version of the Bully
  algorithm. It handles the "Split-Brain" problem by requiring a 
  majority quorum (n/2 + 1), a concept introduced in T2 Agreement Protocols.

PART III: T2 DEEP DIVE - ADVANCED COORDINATION
--------------------------------------------------------------------------------

3.1. AGREEMENT PROTOCOLS AND THE BYZANTINE GENERALS
The Byzantine Generals Problem (T2) is the cornerstone of distributed trust.
- The Malicious Failure Mode: NEXUS allows users to set a server to 
  "Byzantine" mode. In this state, the server returns "Value Failures" (T2) 
  by corrupting the simulated response data.
- Consensus via Raft: The control plane nodes must reach consensus on the
  state of the server list. This ensures that even if one control node 
  experiences a "Crash Failure" (T2/12), the load balancer remains 
  operational (Availability vs. Reliability, T2/8-9).

3.2. FAULT TOLERANCE AND RECOVERY
Lecture T2 defines "Dependability" as Availability + Reliability + Safety.
- NEXUS Availability: Measured as the ratio of successful requests to total
  requests.
- NEXUS Reliability: Simulated via the "MTBF" (Mean Time Between Failures)
  of the server nodes.
- Backward Recovery (Checkpointing): The "Reset" button in NEXUS is a
  coordinated checkpointing event. It brings the system back to the 
  "Recovery Line" (T2/67).
- Forward Recovery: The Auto-Scaler proactively "Heals" the system by 
  allocating new resources to mask the performance degradation of failing 
  nodes.

3.3. CONSISTENCY AND REPLICATION
The IP Hash algorithm is the primary tool for exploring consistency (T2).
- Eventual Consistency: Requests are eventually processed, but client-centric
  consistency (Read-your-writes) is maintained via sticky sessions.
- Replication: NEXUS simulates request replication when "Mirroring" mode
  is enabled (Future Roadmap feature), allowing for Triple Modular 
  Redundancy (TMR) comparisons (T2/18).

PART IV: T3 DEEP DIVE - CLOUD COMPUTING
--------------------------------------------------------------------------------

4.1. THE NIST MODEL AND CLOUD CHARACTERISTICS
NEXUS is a direct mapping of the NIST Cloud definition (T3/6).
- Rapid Elasticity: The core simulation of adding/removing nodes.
- Measured Service: The Analytics dashboard maps to "Pay-as-you-go" 
  monitoring.
- Resource Pooling: The server group acts as a "Multi-tenant" backend (T3/20).

4.2. VIRTUALIZATION AND CONTAINERIZATION
- Virtual Machine Monitor (VMM): The NEXUS Simulation Engine acts as a 
  lightweight VMM, managing the lifecycle of "Guest" ServerNodes (T3/32).
- Docker: The project includes a Dockerfile, mapping to the "Container Cube"
  infrastructure (T3/44) that provides "mobility and congeniality" to the
  deployment environment.

4.3. SERVICE ORIENTED ARCHITECTURE (SOA)
NEXUS exposes its features via a RESTful API (app/api/), mapping to the 
"RESTful Web Services" lecture (T3/31). This allows external "Autonomic 
Systems" (T3/29) to control the simulation programmatically.

SECTION 1: THE NATURE OF DISTRIBUTED COMPUTING
Distributed computing is a field of computer science that studies distributed
systems. A distributed system is a system whose components are located on 
different networked computers, which communicate and coordinate their actions
by passing messages to one another from any system. The components interact with
one another in order to achieve a common goal. Three significant challenges of
distributed systems are: maintaining concurrency of components, overcoming the
lack of a global clock, and managing the independent failure of components. 

NEXUS addresses the "Lack of Global Clock" (T1/10) by providing a unified 
"Global Tick" that ensures all simulated components agree on the current state
of time. This is critical for calculating Request Per Second (RPS) and latency
consistently across all virtual nodes.

SECTION 2: AGREEMENT AND CONSENSUS
Agreement protocols are the method by which a set of processes reach a common
decision in the presence of failures. In NEXUS, this is realized through the
Raft Consensus implementation. Raft ensures that the Load Balancer's 
configuration (the set of active servers) is agreed upon by a majority of 
control plane nodes. This prevents the "Split Brain" scenario where two 
balancers might try to route traffic to conflicting sets of servers.

SECTION 3: FAULT TOLERANCE MODELS
NEXUS implements the "Crash-Stop" and "Byzantine" failure models. 
- Crash-Stop: A server simply stops responding. NEXUS detects this via 
  "Passive Health Checks" and marks the node as UNHEALTHY.
- Byzantine: A server responds with incorrect data. Future versions of NEXUS
  could implement a "Voting Balancer" to mask these arbitrary failures 
  using the 2k+1 replica rule (T2/23).

SECTION 4: CLOUD CHARACTERISTICS (NIST)
The NIST definition (T3/6) of Cloud Computing identifies "Ubiquitous Network
Access" as a key characteristic. NEXUS implements this by exposing a Web
Dashboard and a public REST API, allowing any authorized client to interact
with the simulation from any location.
